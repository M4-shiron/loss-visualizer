# 改善フェーズ計画

Web版MVP公開後の改善フェーズについて、方針・順序・境界を定める。

## このファイルの位置づけ

- `PRODUCT_SPEC.md`はMVPで確定した体験と機能の正本であり、**書き換えない**。
- このファイルは、そこへ**上乗せする改善方針**の正本である。両者が食い違う場合はこのファイルを優先する。
- 改善方針をここに集約し、各Loopでは**差分だけ**を計画に書く。仕様全文をコピーしない。

## 前提

- Web版MVPは第1〜11ループで完成し、2026-08-31にVercelへ公開済み（https://loss-visualizer.vercel.app ）。
- MVPの完成条件（`PRODUCT_SPEC.md`§24）は達成済み。改善フェーズは「動くものを良くする」段階である。
- 引き続き、バックエンドなし・アカウントなし・クラウド同期なし・広告なし・実課金なしで動く状態を維持する。

## 改善方針1: チクチク文の強化（パーソナライズ介入）

購入前の問いかけを、抽象的な一般論から**ユーザー自身のデータを使った具体的な代替提案**へ寄せる。

- 価値尺度・節約目標・履歴など、**ユーザーが登録した実データ**を使った提案を最優先する。
- 方向性は「**言い訳を崩す＋別の使い道を提示する**」。
  - 例：「その3,000円、モニターに回した方が満足しない？」
- 抽象的な問いかけ（`seed/prompts.json`）は、パーソナライズできないときのフォールバックとして残す。
- **AI APIは使わない。** テンプレート＋ユーザーデータの組み合わせで作る。
- **罪悪感を煽らない。説教調にしない。** `PRODUCT_SPEC.md`§0の「買った利用者を責めない」方針は維持する。

## 改善方針2: デザイン改善（感情設計）

**既存の機能・情報構造・基本フローは維持する。** 変えるのは見せ方と感情の起伏である。

- 全体の単調さを改善する。現状はどの画面も同じトーンで、体験の山谷がない。
- **「揺さぶり画面」と「やめる後の報酬画面」の感情差を強くする**ことを最重要とする。
  - **揺さぶり**：静かで、少し緊張感がある。金額とパーソナライズ文を主役にする。
  - **報酬**：明るく達成感がある。守った金額・累計・目標進捗・ゲージ更新を気持ちよく見せる。
- 全体はミニマル＋軽いゲーム感。**幼くしない、派手にしすぎない。**
- 配色、余白、タイポグラフィ、カード、アニメーションの細部は**実装側の裁量**で決める。逐一確認を求めない。
- Claude Design等のデザイン機能を使うかは、**実装前に導入メリットを評価して決める。導入自体を目的にしない。**

## 改善方針3: 労働時間換算

- ユーザーが**任意で**概算時給を登録できる。
- 購入金額 ÷ 時給で概算労働時間を計算し、**約5分単位**で表示する。
- **未登録時は表示しない。** 登録を催促しない。
- 厳密な手取り計算や税計算はしない。概算でよい。
- 単なる「約2時間30分」で終わらせず、**価値尺度や目標と組み合わせた代替提案型**を優先する。
  - 例：「この3,000円は約2時間30分働いた分。モニターに回した方が満足しない？」
- 比較の優先順位は **個人価値尺度 → 節約目標 → 労働時間 → 一般比較** を基本とする。
- 情報過多になる場合の表示選択（何件出すか、どれを省くか）は実装側で合理的に判断してよい。

### 既存方針との整合

READMEの非対象機能にある「将来の年収や職業を断定する金額換算」**とは別物**である。非対象なのはアプリが収入を推定・断定することで、この機能は**ユーザー自身が入力した値**を使う単純な割り算である。

## 改善方針4: 将来のPro設計（準備のみ）

- 第一候補は「**基本無料＋Pro買い切り**」。サブスクは現時点で採らない。
- **現時点で課金SDKや実課金は実装しない。** 設計と境界の整理だけを行う。
- **無料版だけで「衝動買いを止める」核心体験が十分成立すること**を絶対条件とする。
- Proの課金軸は「**機能を塞ぐこと**」ではなく「**パーソナライズの深さ**」。

| | 内容 |
|---|---|
| **無料に残す** | 基本の購入判断フロー、価値尺度、節約目標、履歴、基本グラフ、実績、保留 |
| **Pro候補** | 労働時間換算 / 価値尺度・目標・履歴を複合利用した高度なパーソナライズ介入 / 過去行動ベースの比較 / 詳細分析（カテゴリ傾向、買う・やめる比率、購入理由、節約ペース、目標到達予測など） |

## Loop順序

原則としてこの順で進める。

| Loop | 名称 | 対応する方針 | 主な成果物 |
|---|---|---|---|
| 12 | Personalized Intervention | 方針1 | ユーザーデータを使った代替提案の生成ロジックと表示 |
| 13 | Emotional UI Redesign | 方針2 | 揺さぶり画面と報酬画面の感情差、全体のトーン調整 |
| 14 | Labor Time Comparison | 方針3 | 時給設定と労働時間換算、比較優先順位への統合 |
| 15 | Pro Architecture Preparation | 方針4 | 無料/Pro境界の整理と、課金なしで切り替えられる内部構造 |
| 16 | Release Readiness | — | 公開品質の仕上げ（アイコン・ホーム画面追加・OGP・データの扱いページ・配信ヘッダー）。2026-10-02にユーザーの依頼で追加 |
| 17 | Real Usage Review | — | 実利用にもとづく振り返りと次の判断 |

### 順序を入れ替えてよい場合

Loop 12とLoop 14はどちらも比較カードの生成に手を入れる。**Loop 13の再設計が比較カードの構造そのものに大きく及ぶと判明した場合に限り**、14を13の前へ入れ替えてよい（同じ箇所を二度作り直さないため）。入れ替える場合は`docs/loop-log.md`に理由を残す。それ以外の入れ替えは行わない。

### 各Loopの共通の完了条件

- 受け入れ条件を満たす（Loop計画に毎回明記する）
- テスト・型チェック・lint・本番ビルドがすべて成功
- 主要フローの動作確認
- `docs/loop-log.md`に記録

## 改善フェーズでやらないこと

MVPと同じく、次は追加しない。判断に迷ったら追加しない側に倒す。

- バックエンド、アカウント、クラウド同期
- AI API（問いかけ・文章生成をLLMに任せること）
- 重い分析基盤
- 不要なライブラリ
- 早すぎる課金実装（課金SDK、実際の支払い導線）
- 家計簿機能、銀行・カード連携、SNS共有、ランキング

## データ保存の扱い

**localStorageのスキーマを変更するときは、既存データを壊さないこと。**

- 既存ユーザーの履歴・節約額・実績は失われてはならない。
- 追加フィールド（例：時給）は**任意項目**として足し、未設定でも動くようにする。
- 構造を変える場合は`schemaVersion`を上げ、**migrationまたは後方互換**を実装する。
- `src/storage/validate.ts`の検証を通らないデータは初期化される。追加項目が既存データを弾かないことを必ずテストする。
